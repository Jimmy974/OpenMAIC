# Design: Signed identity login, family roles and course sharing for OpenMAIC

Generated by /office-hours on 2026-09-26
Branch: feat/tailscale-identity
Repo: Jimmy974/OpenMAIC (fork of THU-MAIC/OpenMAIC v1.1.0)
Status: APPROVED
Mode: Startup (intrapreneurship + family use)

## Problem Statement

OpenMAIC v1.1.0 has no sign-in. Every browser gets an anonymous `anonymous_id`
cookie (`Max-Age=30d`, minted once, never refreshed) and every course, folder,
material and agent session is owned by that cookie. Reading a course needs only
its id. Observed on the family deployment today: the parent could not find the
five courses built in another browser; the only way back was pasting
`/classroom/<id>` links, and those links let anyone on the tailnet read any
course. The parent wants per-person libraries, to see what a student builds and
how the student does, and to share courses with specific people.

## Demand Evidence

- One real, observed failure: the parent could not find existing courses from
  their own browser (2026-09-26).
- The parent asked for sign-in, a parent view of "everything", and sharing to
  other signed-in students.
- No student has used OpenMAIC yet, and no company user has either. Sharing
  and the company use case are therefore unvalidated.

## Status Quo

The parent actively uses the family deployment (five courses and two agent
sessions exist) and gets back to courses by pasting `/classroom/<id>` links.
The student side and the company side have not used it yet.

## Target User & Narrowest Wedge

- Users: the parent (admin) and a GCSE student in the same family, each with
  their own Tailscale account and their own device. Company colleagues are a
  later, separate deployment.
- The parent chose the full scope over a smaller wedge (sign-in plus parent
  view), accepting the extra fork code to maintain.

## Constraints

- Must stay mergeable with upstream: new files preferred; touched upstream
  files are listed in "Upstream touch points".
- Upstream behaviour must be unchanged when the feature is off: no new requests,
  `/api/auth/*`, `/api/admin/*` and `/api/shares/*` answer 404, bootstrap and
  every existing route behave as today.
- Deployment: Docker Compose on one Debian host, reached only through
  `tailscale serve` (HTTPS, tailnet-only). No Docker on the dev Mac; tests run
  under Node 22 on the Mac.
- Company content must not flow through the home box or the personal Grok
  subscription.

## Premises (agreed in session)

1. Identity comes from each person's Tailscale account, as a tailnet member or
   as an external user of a node share (Tailscale documents that Serve fills
   the identity headers for users who accepted a share; not yet live-tested
   here). The identity layer is provider-neutral so a company deployment can
   later use company SSO on its own infrastructure. (agreed)
2. Course reads are access-controlled: owner, admins (parents) and people the
   course is shared with. A link alone is not enough. (revised from "anyone
   with the link")
3. Trust boundary: only `tailscaled` may assert identity. Other containers and
   non-root host processes cannot forge one, even by talking to the bridge or
   the app port directly. Root on the host is trusted (it controls the box
   anyway). (revised from "trust loopback headers")
4. Quiz attempts and chat history follow the person across devices, and a
   parent can see a student's quiz results. The existing five courses and two
   agent sessions move to the parent's account. (revised)
5. Identity is per device: whoever is signed in to Tailscale on a device is
   that person on the site. Each family member uses their own signed-in device;
   a shared device logged in as the parent acts as the parent. The identity
   chip always shows who the site thinks is signed in.

## Approaches Considered

- **A: Tailscale headers read inside the app** (bridge only adds a secret).
  Smallest diff, but the company version would have to rewrite identity code.
- **B: Bridge reads Tailscale, app trusts a signed provider-neutral identity.**
  Chosen.
- **C: Built-in OIDC login (Auth.js with Google/Microsoft).** Most portable,
  but largest effort and security surface (sessions, CSRF, secrets). Rejected
  for now.

## Recommended Approach (B)

```
browser ─https─▶ tailscale serve (root) ─▶ identity-bridge (host 127.0.0.1:3001, runs as clawdbot)
                   strips forged             1. peer check: TCP peer socket uid must be 0 (tailscaled),
                   identity headers             read from /proc/net/tcp{,6}; otherwise 403
                                             2. drops every inbound X-OpenMAIC-Identity-* header
                                             3. Tailscale-User-* (RFC2047-decoded) → signed contract
                                                   │
                                                   ▼
                                     openmaic app (127.0.0.1:3000 → container)
                                     verifies HMAC + freshness in route/server code
```

### 1. Identity contract (provider-neutral)

- Server env: `AUTH_MODE=signed-header`, `AUTH_IDENTITY_SECRET` (≥32 bytes,
  base64/hex), `AUTH_ADMIN_LOGINS` (comma-separated, required and non-empty),
  optional `AUTH_MAX_SKEW_SECONDS` (default 300).
- Build-time client switch: `NEXT_PUBLIC_AUTH_MODE=signed-header` (Dockerfile
  `ARG`/`ENV` + compose build arg, like `NEXT_PUBLIC_PERSISTENCE`). With it
  unset the client makes no auth calls.
- Headers from the bridge: `X-OpenMAIC-Identity-Login`,
  `X-OpenMAIC-Identity-Name` (UTF-8, percent-encoded), `X-OpenMAIC-Identity-Avatar`,
  `X-OpenMAIC-Identity-Timestamp` (epoch seconds), `X-OpenMAIC-Identity-Signature`.
- **Signed input**: `v1\n<login>\n<name>\n<avatar>\n<timestamp>` using the exact
  header values as transmitted (the name stays percent-encoded; absent fields
  are the empty string). Signature = lower-case hex HMAC-SHA256 with the secret.
- **Normalisation**: login is trimmed and lower-cased before signing (the
  bridge does this) and again on read; admin matching uses the same normalised
  login.
- **One verifier**: `lib/server/auth/signed-identity.ts` uses `node:crypto`
  (`createHmac` + `timingSafeEqual`), synchronous, used by routes and server
  actions. Middleware does **not** verify (see §3). Shared test vectors in
  `tests/fixtures/signed-identity-vectors.json` (ASCII name, RFC2047 Chinese
  name, empty avatar, stale timestamp, tampered login) are used by both the
  app tests and the bridge tests.
- **Owner id**: `acct_` + first 32 hex chars of SHA-256(normalised login). 37
  characters, collision-resistant (128 bits), fits the shared-owner pattern,
  never `anon:`. `auth_members.login` is unique; if an existing row with the
  same `owner_id` has a different login, sign-in fails with 500 and a logged
  error instead of aliasing (a 128-bit collision, effectively never).
- **Learner key**: the member's learner key is the same `acct_…` string.
- Startup validation in `instrumentation.ts`: unknown `AUTH_MODE`, short or
  missing secret, empty `AUTH_ADMIN_LOGINS`, or `AUTH_MODE` together with
  `PERSISTENCE_SHARED_OWNER_ID` fails boot.

### 2. Owner resolution (authoritative enforcement)

- `resolveRequestOwnerId` keeps its signature. With auth on and no explicit
  `authenticatedOwnerId`, it verifies the signed identity and returns its owner
  id without minting a cookie; with no valid identity it throws
  `UnauthenticatedError`.
- `withRequestOwnerId` maps `UnauthenticatedError` to
  `401 { errorCode: 'AUTH_REQUIRED' }`. That covers every route that goes
  through it (stage-meta, materials, stages, stages/[id]/*, agent sessions,
  skills, persistence, folders).
- The three direct callers get the same mapping via a shared
  `ownerIdOr401(req)` helper: `app/api/stages/[id]/freshness/route.ts`,
  `app/api/agent/owner-events/route.ts`,
  `app/api/agent/sessions/[id]/events/route.ts`.
- `lib/workbench/workspace-actions.ts#currentOwnerId` reads `headers()`,
  verifies, and throws `UnauthenticatedError` (the action returns
  `{ deleted: false }` to the client).

### 3. Middleware (UX gate only)

Middleware may run where server env is not reliably visible, so it never
decides identity. With `NEXT_PUBLIC_AUTH_MODE` set it only checks that
`X-OpenMAIC-Identity-Signature` is present: API requests without it get 401,
page requests get a static "Open this site through Tailscale while signed in"
page, `/api/health` stays open. A forged-but-present header passes the gate and
is refused by the route-level verifier. `ACCESS_CODE` stays independent.

### 4. Read access control

`canReadStage({ ownerId, viewerOwnerId, viewerIsAdmin, isSharedWithViewer })`
returns true for owner, admin or share recipient. Every denial answers
**404** (the same as missing or tombstoned), so existence is never disclosed.
Applied only when auth is on:

| Read path | Today | With auth |
|---|---|---|
| Persistence `GET /documents/<id>` and scenes (`decideDocumentAccess`) | by id | `canReadStage` via new optional `canReadForeign` callback |
| `GET /api/stages/[id]`, `/scenes` (owner-bound store `readGated`) | by id | `canReadStage` inside `readGated` (one gate for both routes and the load step of PATCH/PUT) |
| `GET /api/stages/[id]/manifest`, `/freshness` | owner-only | unchanged |
| `GET /api/stage-meta/[id]` (existence, isOwner, publish state) | by id | `canReadStage`, else 404 |
| `GET /api/stages/[id]/status` (existence, publish state) | by id | `canReadStage`, else 404 |
| `POST /api/stages/[id]/publish`, `/unpublish` | owner-only, UI never calls them | disabled (404) in auth mode; `is_public` is not a read grant |
| `GET /api/classroom?id=`, `/api/classroom-media/*`, `GET /api/generate-classroom/[jobId]` (file-based classrooms from the external skill API, no owner) | by id | admin only, else 404 |
| Agent-runtime tools (`read_stage`, `@` course refs, previews, history) | owner-checked (`withOwnerStageAuthorization`, `probeStageAccess`) | unchanged |
| Persistence `/assets` bytes | shared principal | unchanged; residual: asset ids are unguessable and only appear inside access-controlled documents |
| Export (PPTX, ZIP, video) | built in the browser from data already loaded | unchanged |

### 5. Members, parent view, sharing

- `auth_members(owner_id PK, login UNIQUE, display_name, avatar_url,
  first_seen_at, last_seen_at)`, upserted by `GET /api/auth/me`, which returns
  `{ member: { login, name, avatarUrl, ownerId, learnerKey, isAdmin } }`
  (`ownerId === learnerKey`).
- `GET /api/auth/members` (signed-in) → `[{ login, name, avatarUrl }]` for the
  share picker.
- `course_shares(stage_id, owner_id, recipient_owner_id, created_at,
  PRIMARY KEY (stage_id, recipient_owner_id))`.
  - `GET /api/stages/[id]/shares`, `POST … { login }`, `DELETE …?login=`:
    owner only (non-owner → 404); recipient must be a registered member and not
    the owner (400).
  - `GET /api/shares/incoming` joins `stage_meta` and `document_stages` and
    excludes `deleted_at IS NOT NULL`, so deleted courses drop out; share rows
    are also deleted when a course is tombstoned.
- Admin (every route 404 for non-admins):
  - `GET /api/admin/members` → members with course counts.
  - `GET /api/admin/members/[ownerId]/stages` → that member's courses.
  - `GET /api/admin/members/[ownerId]/quiz-results` → every `quizAttempt`
    runtime session whose `learner_key` is the member's key, across **all**
    stages (including courses owned by others and shared with them). Per
    attempt: stage name, scene, phase, `earned` = sum of `results[].earned`,
    `total` = sum of question `points ?? 1` from that quiz scene in the stage
    document, submitted time. Attempts with no `results` show "in progress".
    `earned` is client-graded (upstream grades in the browser); residual.
- UI:
  - Header identity chip (avatar, name, "Parent" badge for admins).
  - Home: **Shared with me** section.
  - Classroom header: a **Share** button beside the existing Export menu
    (owner only; there is no existing Share/Publish UI) → dialog with member
    picker and current recipients.
  - **Family** page (`/family`, admins only): members → their courses and
    their quiz results (grouped by course, whoever owns it).

### 6. Learner data follows the person

- Server (`app/api/persistence/[...path]/route.ts`): with auth on, `/runtime`
  requests authenticate from the signed identity: principal
  `{ key: shared, learnerKey: acct_… }`. The dev token is not required in auth
  mode. A path learner key that differs is refused by the storage server's
  existing `forbiddenLearner` check (403, runtime paths only; documents and
  assets are unaffected).
- Client (`lib/persistence/bootstrap.ts`), only when
  `NEXT_PUBLIC_AUTH_MODE` is set: `getPersistenceLearnerKey()` resolves the
  account key from `/api/auth/me` (memoised) instead of the device KV, and the
  same provider is passed as `learnerKey` to `configureRuntimeStorage`. Both
  paths therefore send and use the account key.
- Migration of a device's pre-login attempts: `authorizeMerge` allows
  `mergeLearner(from, to)` only when `to === principal.learnerKey` and `from`
  starts with `anon:`. After sign-in, if the device KV holds an `anon:` key, the
  client calls merge once. The server treats an empty source as a no-op, so the
  call is safe unconditionally. The device key is removed only after a
  successful merge. Residual: anyone who knows another device's random anon key
  could claim its pre-login attempts.

### 7. Existing data

- Owner-keyed tables: `stage_meta`, `document_stages`, `document_folders`,
  `agent_sessions`, `agent_user_skill`, `owner_material`,
  `agent_owner_session_events`, `agent_owner_session_event_counters`; learner
  data in `runtime_sessions.learner_key`.
- `scripts/reassign-owner.sql` takes `(from_owner, to_owner)` pairs and, in one
  transaction, moves `stage_meta`, `document_stages`, `document_folders`,
  `agent_sessions`, `agent_user_skill`. It aborts if either source owner has
  `owner_material` rows (none exist today, and their object keys embed the
  owner id, so moving them needs a byte migration that is out of scope).
- Left in place: `agent_owner_session_events` and `…_counters` are the live
  sidebar feed keyed by owner; old rows are never read again and the new owner
  starts a fresh feed. Session history (`agent_session_events`,
  `agent_session_entries`) is keyed by session id, and the route checks the
  session's owner, so it stays readable after the move.
- Mapping for this deployment: both existing test owners → the parent. Any
  course the student builds before cut-over is mapped to the student's account
  with the same script.
- Run after `pg_dump`; post-check: every moved stage opens for the parent.

### 8. Bridge operation

- `scripts/identity-bridge.mjs`, no dependencies, Node ≥ 22 (host already has
  Node 24 at `/usr/local/bin/node` for `grok-relay`). Runs as a systemd user
  service like `grok-relay` (linger is enabled for the service user),
  `Restart=always`. Unit file shipped in `scripts/`.
- Peer check is Linux-only: on other platforms the bridge refuses to start
  unless `BRIDGE_ALLOW_ANY_PEER=1` (dev only).
- Streams request/response bodies (SSE included) and passes WebSocket upgrades.
  Requests without Tailscale identity headers (tagged devices) are forwarded
  unsigned; the app answers 401 and the notice page.
- `GET /__bridge/health` (served by the bridge itself, subject to the same peer
  check) and a check in the ops notes that fetches the site through Serve.
- `tailscale serve` target changes from `:3000` to `:3001`. The app port stays
  published on 127.0.0.1 only. No Docker network changes in v1.

## Success Criteria

With two real members (parent = admin, student) plus a third simulated
non-admin member signed directly with the secret in integration tests:

- The parent opens the site on two devices and sees the same library,
  including the five existing courses.
- The student cannot read the parent's unshared course: every read path in §4
  answers 404. After the parent shares it, it appears under the student's
  Shared with me and opens; after unsharing, it answers 404 again.
- The third member gets 404 on both the parent's and the student's unshared
  courses; the parent (admin) can open the student's courses and sees them on
  the Family page.
- A quiz attempt the student makes on device A shows on device B and in the
  parent's Family page with earned/total.
- A request to the bridge from a non-root process, or to the app port with
  forged `X-OpenMAIC-Identity-*` or `Tailscale-User-*` headers, never yields
  a signed-in identity (403 at the bridge, 401 at the app).
- Feature off: the full upstream test suite passes unchanged, and no new
  requests are made by the client.

## Reviewer Concerns

### R2-1 — feasibility

**Problem**

> The Section 8 peer check admits any TCP peer whose socket uid is 0. A container that uses host networking and runs as root (Docker's default without userns-remap) shares the host network namespace, and its sockets appear as uid 0 in /proc/net/tcp. It therefore passes the check, can send Tailscale-User-Login set to the parent's login, and receives a signed admin identity. This is the host-network case from R1-1, and it contradicts Premise 3 ('Other containers ... cannot forge one'). In addition, the success criterion's bridge test has nowhere stated to run: the peer check is Linux-only, and tests run on the Mac.

**Remedy**

> Either record in the ops notes that no container on the host runs with host networking as root (and name any allowed ones as trusted in Premise 3), or make the boundary independent of uid 0, for example a Serve target on a Unix socket with restrictive permissions if the installed tailscale serve supports one. State where the boundary test runs: /proc/net/tcp parsing against fixtures on the Mac, plus live probes on the Debian host from a non-root process and from a host-network container.

### R2-2 — feasibility

**Problem**

> The bridge runs as the clawdbot user service and needs AUTH_IDENTITY_SECRET to sign, and the app gets the same secret through the compose environment. Any process running as clawdbot (grok-relay, an agent run by that user, or anything that compromises either) can read the secret from the unit's environment file or /proc/<pid>/environ. So can anyone who can read the compose env file or run docker inspect. With the secret, any of them can sign the parent's login and call 127.0.0.1:3000 directly. That contradicts Premise 3 ('non-root host processes cannot forge one, even by talking to the bridge or the app port directly') and makes the forged-header success criterion incomplete. The design never says where the secret is stored or who can read it.

**Remedy**

> Specify where the secret lives on the host and who can read it. Either run the bridge as a dedicated system user that runs nothing else, with the secret from a root-owned credential (for example systemd LoadCredential=) and a compose env file readable only by root, or narrow Premise 3 and the success criterion to name the bridge's service user and docker-group members as trusted.

### R2-3 — completeness

**Problem**

> Section 4 keeps the file-based classrooms that the external skill API produces (/api/classroom, /api/classroom-media, /api/generate-classroom/[jobId]) as admin-only reads, but never says what happens to the skill API's own client in auth mode. Middleware answers 401 to any API request that lacks X-OpenMAIC-Identity-Signature, and Serve sends requests from tagged devices unsigned. A skill client that creates a job at /api/generate-classroom or polls it, whether on 127.0.0.1:3000 or from a tagged node through Serve, therefore stops working, and the design does not say whether that is intended.

**Remedy**

> State whether the external skill API is used on this deployment. Then either declare it unsupported in auth mode (and 404 its routes), or define how that client authenticates (for example a separate service credential checked at the route and exempted in middleware) and which member owns the classrooms it creates.

### R2-4 — consistency

**Problem**

> The Section 4 table lists GET /api/stages/[id]/manifest and /freshness as 'owner-only' today and 'unchanged' with auth. Both routes call store.readFreshnessManifest, which lib/persistence/owner-bound-document-store.ts runs through the same readGated capability-by-id read as loadDocument ('The trigger-maintained freshness manifest is a read: capability-by-id'). So they are readable by id today, and putting canReadStage inside readGated changes them as well. If the row is taken literally and the manifest is kept outside the new gate, any member can read another member's scene ids and revisions, and the 200/404 difference confirms that a course exists. That defeats Premise 2 and the every-read-path-404 criterion.

**Remedy**

> Correct the row: today these routes are capability-by-id through readGated, and with auth they are gated by canReadStage through readGated (owner, admin and recipients get live refresh; everyone else gets 404). Include both routes in the student's 404 success check.

### R2-5 — completeness

**Problem**

> Server AUTH_MODE and the build-time NEXT_PUBLIC_AUTH_MODE are independent switches, and the startup validation in Section 1 does not check that they agree. An image built without NEXT_PUBLIC_AUTH_MODE but run with AUTH_MODE keeps the device's anon: learner key while the server principal is acct_..., so every runtime request (quiz attempts, chat) fails with 403 FORBIDDEN_LEARNER without any visible error, and the middleware gate is off. The reverse case makes the client call /api/auth/me, receive 404, and fail learner-key resolution.

**Remedy**

> Fail boot in instrumentation.ts when AUTH_MODE and the inlined NEXT_PUBLIC_AUTH_MODE disagree, and add that case to the startup-validation tests.

### R2-6 — completeness

**Problem**

> auth_members, course_shares, the cross-device learner data in Section 6 and the admin quiz-results query all need server persistence. Section 6's client changes also run only inside isBrowserPersistenceEnabled() (NEXT_PUBLIC_PERSISTENCE=1). Startup validation does not require DATABASE_URL or the persistence build flag when AUTH_MODE is set. An auth-mode deployment without them either fails per request or quietly keeps quiz attempts on the device, which breaks Premise 4.

**Remedy**

> State that signed-header mode requires server persistence, and fail boot when AUTH_MODE is set without DATABASE_URL, or when NEXT_PUBLIC_AUTH_MODE is set without NEXT_PUBLIC_PERSISTENCE=1.

### R2-7 — consistency

**Problem**

> Section 7 says any course the student builds before cut-over (the Assignment's GCSE lesson) is moved to the student with the same script, but the script aborts whenever a source owner has owner_material rows. If the student uploads source material while building that lesson and it is stored as owner material, the student's pair aborts and the lesson cannot be moved. The only post-check is that moved stages open for the parent.

**Remedy**

> Pick one: tell the student not to upload materials during the Assignment, declare such a lesson disposable, or include its material byte migration. Extend the post-check so that each moved course opens for its new owner, including the student's.

### R2-8 — feasibility

**Problem**

> The reassignment rewrites stage_meta, document_stages and agent_sessions owners while the app may be running. The agent runner leases sessions and writes through an owner-bound store bound to the session's owner, so a run in progress during the move would have its writes refused as foreign, and requests arriving mid-move can create content under the old anon owner. Section 7 only says to run the script after pg_dump. The cut-over order (stop, dump, reassign, deploy the auth build, start the bridge, switch the Serve target) is not stated.

**Remedy**

> Write the cut-over sequence: stop the app so the runner is idle, pg_dump, run the reassignment, deploy the auth-mode build and the bridge, switch tailscale serve to :3001, start the app, run the post-checks, and roll back from the dump if a check fails.

### R2-9 — feasibility

**Problem**

> Premise 1 and Dependencies still offer node sharing as a way to join, backed by a claim about Tailscale's documentation that the design itself says is 'not yet live-tested here'. No step verifies that a node-shared user's request reaches the bridge with Tailscale-User-Login populated. If it does not, a family member who joins by node share only ever sees the notice page.

**Remedy**

> Add a live check to the Assignment or cut-over checklist: one request from a node-shared account showing the Tailscale-User-* headers at the bridge. Until it passes, mark node sharing as unsupported in v1 and list only tailnet invites.

### R2-10 — clarity

**Problem**

> Section 2 describes the 401 AUTH_REQUIRED mapping only for withRequestOwnerId, the three direct callers and currentOwnerId. GET /api/stages/[id]/status and the three file-classroom routes resolve no owner today, yet Section 4 now gates them on canReadStage or admin status. The design does not say how they verify the signed identity or what they return when it is missing, forged or stale (401, or the 404 used for denials). Middleware checks only that the header is present, so a forged header reaches these routes.

**Remedy**

> State that these routes, and the new /api/auth, /api/admin and /api/shares routes, verify through the shared ownerIdOr401 helper: 401 AUTH_REQUIRED for a missing or invalid identity, then 404 for a failed access check. Include them in the forged-header test.

### R2-11 — completeness

**Problem**

> The admin quiz-results route computes total from 'that quiz scene in the stage document'. The runtime contract (packages/@openmaic/dsl runtime.ts) says sceneId anchors are best-effort and may dangle after edits, and attempts can refer to courses that were later tombstoned. The design does not define what the Family page shows when the quiz scene was deleted or its questions changed, or when the course is tombstoned.

**Remedy**

> Define the behavior: for example, show earned with total 'unknown' (or earned against the current total, flagged) when the scene is missing or changed, and state whether attempts on tombstoned courses are listed, labeled deleted, or hidden.
